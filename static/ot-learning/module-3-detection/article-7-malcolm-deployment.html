Deploying Malcolm for OT Traffic Visibility

Published: 2026-10-01 · Module: Module 3, Article 7: Detection Engineering · Code: github.com/mhebert-security/malcolm-ot-lab

In the last article I wrote three Sigma rules for ICS ATT&CK techniques and admitted they had only been tested against traffic I generated in my own lab. That admission stayed with me. A detection rule without a stream of real traffic feeding it is a hypothesis, not a control. So the next step in my learning path was not to write more rules. It was to build the layer that makes OT traffic visible in the first place.

That layer is Malcolm. This article is the walkthrough of how I deployed it, what I had to change on my network to feed it OT traffic, and what that traffic actually looks like once Malcolm has parsed it into logs I can query.

What Malcolm Actually Is

Malcolm is an open-source network traffic analysis suite published by the Center for Internet Security. It is not a single program. It is a packaged set of four tools that each do one job well and that share a common data store.

The four core components are Zeek, Suricata, Arkime, and OpenSearch. Zeek, which I introduced in the last article, is a network security monitor that parses protocols off the wire and writes structured logs. Suricata is a signature-based intrusion detection engine that flags known malicious patterns. Arkime is a full packet capture indexer that lets me pull the raw bytes of any session I want to inspect after the fact. OpenSearch is the search backend all three of the others write into, and the Malcolm deployment also ships a Dashboards interface on top of it so I can query everything from a browser.

The reason Malcolm matters for OT work specifically is that its Zeek build includes the ICS Network Protocol Parsers, usually shortened to ICSNPP, a plugin maintained by researchers at Idaho National Laboratory. ICSNPP adds Zeek analyzers for Modbus, DNP3, EtherNet/IP and CIP, S7comm, BACnet, and several other protocols that enterprise deployments of Zeek do not parse by default. A plain Zeek install will show you that two hosts exchanged TCP traffic on port 502. An ICSNPP-enabled Zeek install will show you that the master wrote value 1 to coil address 1024 of unit 3, which is a completely different thing to alert on.

The Deployment

I ran Malcolm on a single Ubuntu 22.04 host with 32 GB of RAM, 8 vCPUs, and a 1 TB SSD. The Malcolm project documentation recommends at least 16 GB of RAM and says that memory, not CPU, is the constraint that will bite you first, and in my experience that is correct. OpenSearch alone wanted most of the memory budget. If you are doing this on a budget, invest in RAM before you invest in CPU.

The installation itself is a git clone and a Python script. I cloned the Malcolm repository from the Center for Internet Security GitHub org, changed into the directory, and ran the install script. The script pulls Docker images, generates a self-signed TLS certificate, and writes a default configuration file. From there, a single docker compose up -d brings the full stack online. The web interface comes up on port 443 of the host, which is a well-known and frankly awkward choice because it conflicts with anything else listening on that port. On my lab host nothing else was, so I left it.

Malcolm can run in two modes. In live capture mode it listens on a network interface and processes every packet as it arrives. In PCAP ingest mode, it watches a directory for packet capture files, which is what the community calls PCAP files, and processes each one as it appears. I used both. Live capture is what a production deployment looks like. PCAP ingest is how I replayed captures I had taken earlier without having to route traffic back through the host.

Network Plumbing for OT Traffic

The single biggest hurdle I hit was not software. It was getting OT traffic to the Malcolm host in the first place. My lab switch is a managed switch that supports port mirroring, which the vendor calls a SPAN port. Mirroring means the switch is configured to send a copy of every frame on the ports I care about out of one dedicated port, which I plugged into a second network interface on the Malcolm host. The Malcolm host then listens on that interface in promiscuous mode, which means it accepts every frame the switch copies to it rather than only frames addressed to its own MAC address.

If your switch does not support port mirroring, the alternative is a network TAP, which is a small physical device that sits inline on a cable and copies all traffic to a second port without modifying the original stream. TAPs are more reliable than SPAN ports because they never silently drop frames under load, but they cost money and they introduce a new failure point in a live process network. For my lab, SPAN was fine.

One thing I want to flag for anyone doing this in a real plant: do not accidentally deploy Malcolm in a way that lets it write to the OT network. The container stack only needs to receive mirror traffic. If your Malcolm host has a second interface on a management network, make sure the OT-facing interface is receive-only from the switch's point of view, or at least that the host's routing table sends nothing out of it. The cost of a mistake here is a research tool accidentally sending a packet to a PLC.

What Modbus Traffic Looks Like Once Malcolm Sees It

The first capture I replayed was a Modbus/TCP session between a Linux host running pymodbus and a simulated PLC I had stood up earlier in this series. In Wireshark the session is readable but tedious: a handful of request/response pairs interleaved with TCP acknowledgments, each one needing to be expanded manually to see what the function code and address were.

Malcolm turns the same session into a single log line. The Zeek modbus.log that ICSNPP produces has one row per Modbus transaction, with columns for timestamp, connection identifier, source IP and port, destination IP and port, function code, unit identifier, the starting address of the operation, and a quantity if the operation covers a range. A write from the engineering workstation to a simulated PLC shows up as a row with function code 16, unit identifier 1, and the address range that was written. A read shows up as function code 3.

The first thing that struck me when I saw this in Malcolm's Dashboards interface was how easy it is to sort and filter. I can search for every function code 5 or 6 in a capture. I can pivot from a suspicious write back to the raw packets in Arkime with one click. I can ask whether the same source IP ever reads from the PLC, which it would if it were an HMI, or only ever writes to it, which is a different behavioral profile entirely. None of that is possible when I am scrolling through packets in Wireshark.

What DNP3 Traffic Looks Like

DNP3 is more structured than Modbus at the protocol level, and the Zeek dnp3.log that Malcolm produces reflects that. Every row has a source IP and port, a destination IP and port, a request function code, a reply function code, and a station address that identifies which outstation the master was talking to. DNP3 masters send one of a known set of function codes such as a read, an operate, or an integrity poll, and the outstation replies with a matching reply code.

Cold restart, which is the function code my T0816 rule watches for, appears as function code 13 in the request column. Warm restart is function code 14. The log line is unmistakable. When I sent a cold restart from the master in my lab, Malcolm recorded it and the Sigma rule from the previous article would have fired against the same data if I had wired the two together.

Filtering DNP3 logs in Malcolm also lets me spot patterns that are hard to see on the wire. A master that repeatedly polls one outstation is normal. A master that starts polling a second outstation it has never talked to before is worth a look. The Dashboards interface makes that kind of comparison a five second query.

What EtherNet/IP Traffic Looks Like

EtherNet/IP is where the parsing starts to get harder, and I want to be honest that I understand this protocol less well than Modbus and DNP3. EtherNet/IP carries the Common Industrial Protocol, usually shortened to CIP, inside a TCP or UDP envelope. CIP defines its own service codes that sit inside the TCP payload, so a Zeek analyzer has to parse two layers deep before it can tell you what was actually requested. The ICSNPP EtherNet/IP analyzer does that parsing, but the resulting logs have more fields and more ambiguity than the Modbus and DNP3 logs do.

In my captures of a couple of Rockwell CompactLogix controllers talking to an HMI, the most useful field turned out to be the source and destination IPs in conn.log combined with the CIP service code in the EtherNet/IP log. A GetAttributeSingle service from an HMI polling a controller is normal traffic and repeats constantly. A WriteTag or Generic Service request originating from anything other than the engineering workstation is not normal, and it is exactly the kind of event that would be invisible without protocol-aware parsing.

I have not yet built Sigma rules for EtherNet/IP. That is the next thing on my list, and it depends on getting the CIP service code names mapped onto the ICS ATT&CK techniques they correspond to.

Suricata's OT Rules

Malcolm also runs Suricata with a rule set that includes several OT-focused signatures. In my lab captures Suricata produced very few alerts, which I interpret as correct behavior rather than a problem. My lab generates clean Modbus and DNP3 traffic with no attacks in it. The rules are there waiting for the day I add a scanning or exploit stage to the lab, and having them on from the start means I do not have to add a detection tool later when I am already in the middle of an incident.

The Suricata alerts land in the same Dashboards interface as the Zeek logs, which is the main operational advantage of Malcolm over cobbling together the tools yourself. One interface, one backend, one place to look.

What I Have Not Validated Yet

This deployment is a lab. I have not run Malcolm against production OT traffic, and the reasons matter for anyone thinking of doing the same.

The first gap is scale. My capture volumes are trivial. A real manufacturing plant or substation produces orders of magnitude more meter traffic, HMI polling, and broadcast noise than my lab does. I do not know how Malcolm behaves when a single day of Zeek logs is larger than my entire testing history. The project documentation and community reports suggest it handles this, but I am going to resist claiming that until I see it.

The second gap is baselining. For OT detection to be useful, an analyst needs to know what normal looks like. I do not have that yet. I can see that a Modbus write happened, but I cannot tell you with confidence whether the analyst on shift would consider it expected. Baselining takes weeks of clean captures and I have weeks of clean captures in the future, not the past.

The third gap is around encrypted or proprietary protocols. Some modern PLCs and RTUs talk over TLS or over vendor-specific protocols that no public Zeek analyzer parses. Malcolm will still log the connection and its metadata, but it will not tell me what was inside. Anyone deploying this in a modern plant should expect a meaningful fraction of traffic to fall into that category.
