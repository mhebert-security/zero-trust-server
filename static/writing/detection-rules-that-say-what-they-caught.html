Detection Rules That Say What They Caught

Published: 2026-09-12 · Code: github.com/mhebert-security/sigma-detections-attck

I wanted to know whether I could write a detection rule that actually worked. Not one that compiled, and not one that looked reasonable on paper, but one that caught a real attack and could prove it. I built a small lab to find out.

Most detection engineering portfolios are collections of YAML files, where YAML is a text format for structured data. Someone read a blog post about a technique, translated it into a detection format, and pushed it to GitHub. The rule has never fired against a real attack, and it has never been tested against actual adversary behavior. It is a hypothesis dressed up as a fact, and the difference matters when an analyst is deciding whether to wake someone up at three in the morning.

I wanted mine to be different, so I made it a rule that every rule in this repository fired against real telemetry, meaning the actual event records a machine produces, before it shipped.

The lab

The infrastructure is two machines. A Windows Server instance running on AWS generates the events. A Wazuh manager, also on AWS, collects and analyzes them.

Wazuh is a security information and event management platform. The short version is that every notable thing that happens on your monitored machines gets sent to Wazuh, which runs it through a ruleset and fires an alert when something matches. Think of it as a very attentive reader who has memorized a long list of things to watch for and never takes a break.

On the Windows machine I installed Sysmon, a Microsoft tool that instruments the operating system at a low level and produces detailed event logs for things the default Windows logging does not capture. Process creation, network connections, registry modifications, file creation, memory access between processes. Sysmon sees things basic Windows event logging pretends not to notice.

Between Sysmon and Wazuh I can watch what happens when an attacker runs a technique and compare it against what my rule expected to see. If the rule fires, I have a validated detection. If it does not, I have a gap to fix.

Atomic Red Team

The adversary in my lab is a tool called Atomic Red Team. It is a library of small, contained attack simulations maintained by a security company called Red Canary. Each simulation is called an atomic test, because it isolates one specific technique from the larger category it belongs to. Running an atomic test generates real telemetry on a real machine without doing anything irreversible or harmful.

This is what separates a tested rule from a hypothetical one. I do not have to imagine what a malicious PowerShell invocation looks like in the logs. I can generate one, watch exactly how Sysmon records it, and write a rule against what I actually saw rather than what I assumed I would see.

The gap between what I assumed and what I observed turned out to be one of the most useful things this project taught me.

The framework behind the labels

MITRE ATT&CK is a public catalog of the techniques real attackers use, organized by phase of an intrusion. Initial access, execution, persistence, credential access, lateral movement. Each technique has an identifier, a description, and documentation of how it has been observed in the wild.

Every rule in this repository maps to a technique in that catalog. That mapping answers a question every alert should answer and most do not, which is what part of an attack the alert represents.

An alert that says "suspicious PowerShell activity" is the beginning of a question. An alert that says "T1059.001: command and scripting interpreter, PowerShell sub-technique, encoded command execution" is a partial answer. An analyst reading it knows which phase of an intrusion they are looking at, what the attacker is trying to do, and what probably comes next if the technique succeeded. That context is what turns a single alert into a story someone can act on instead of a data point they have to interpret from scratch.

How a rule gets written

The format I use is Sigma. Sigma is a vendor-neutral rule specification for security detections. A Sigma rule describes what to look for in abstract terms, and a conversion tool translates it into the native format of whatever platform you deploy to. The same rule can run on Wazuh, Splunk, Elasticsearch, or Microsoft Sentinel without being rewritten for each one.

Every rule I write has the same required fields. A title describing what it detects, a unique identifier, a status field that separates a validated rule from a hypothesis, a description that explains the adversary behavior rather than just the detection logic, references to the relevant ATT&CK technique, the source of the log data it expects, the detection logic itself, a list of known legitimate uses that would produce a false positive, and a severity level.

The false positive list is where most rules reveal whether their author thought seriously about the problem. A rule that lists "legitimate admin activity" as a false positive has not thought seriously about it. A rule that lists "SCCM invoking encoded PowerShell during package deployment" has named a specific scenario a real analyst can look for when triaging an alert. The specificity is what makes the list useful.

The first rule and what it cost me

The first technique I wrote a rule for was T1059.001, PowerShell encoded command execution.

PowerShell accepts a flag called -EncodedCommand that takes a Base64-encoded string and runs it as a command. Base64 is a way of turning binary or unusual text into plain letters and digits. Attackers use the flag to hide what they are running from casual inspection. The command line shows gibberish instead of the payload. It is one of the most common techniques in post-exploitation toolkits and one of the most reliable signals that something is happening that should not be.

Writing the detection logic was straightforward. PowerShell process creation, command line containing the encoded command flag, fire an alert.

Getting it to fire was not.

The first problem was the group name. Wazuh organizes its rules into groups, and a child rule fires only when an event has already been processed by a parent rule in the correct group. I used the wrong group name for Sysmon process creation events. The rule was syntactically valid, logically correct, and completely inert. It never evaluated against anything. The fix was finding the right group name by reading the Wazuh built-in ruleset directly rather than assuming from the documentation.

The second problem was the flag variants. PowerShell accepts abbreviated versions of its flags. -EncodedCommand can be shortened to -EnC, to -EC, or just to -E. The atomic test I ran used -E. My rule only matched the full flag name. Real adversaries use the abbreviations constantly, precisely because they are shorter and less conspicuous. The fix was expanding the regular expression to cover every valid abbreviation.

The third problem was the regular expression itself. Matching -E in a command line is easy to get wrong. A pattern that matches the letter E preceded by a hyphen will also match any flag beginning with E that is not the encoded command flag. The correct pattern anchors to word boundaries and accounts for both hyphen and slash prefixes, because PowerShell accepts both.

By the time the rule fired reliably, I had learned more about PowerShell's command line parsing than the PowerShell documentation ever bothered to explain. That is what testing against real behavior cost me instead of assuming, and it is why the tested version of a rule is worth more than the untested one.

What LSASS taught me about thresholds

The second rule I wrote was for T1003.001, LSASS memory access.

LSASS is a Windows process that handles authentication. It keeps credentials in memory because it needs them constantly. Attackers access LSASS memory to pull those credentials out, a technique made famous by a tool called Mimikatz. It is one of the most heavily documented attack techniques in existence and one of the most reliable indicators that an intrusion has moved past initial access into credential theft.

Detecting it seems simple. Alert when a non-system process opens a handle to LSASS with read permissions. The reality is that dozens of legitimate processes open handles to LSASS constantly. Antivirus software, system management tools, some backup software. The signal is real, but so is the noise.

My rule filters out known legitimate sources by matching the source process image against a list of trusted system paths. Anything from a known system directory with a known trusted name passes without alerting. Anything else fires.

Getting the exclusion list right required running the lab without any detection rules and watching every process that touched LSASS over a period of normal operation. Then I wrote the exclusions against what I actually saw, not against a generic list copied from a blog post. A generic list is someone else's environment. My exclusion list reflects mine.

The rule fires on things that are not on the list and does not fire on things that are. The threshold between those two categories had to be observed before I could set it.

The quality gate

A rule earns the status "test" after three things happen. The Sigma YAML is written. The Wazuh XML translation is deployed and the manager loads it without errors. An Atomic Red Team test fires the technique and the alert appears in the Wazuh dashboard with the correct rule ID.

A rule that passes those three gates is one I can stand behind. I know the telemetry is real because I generated it, I know the rule fires because I watched it fire, and I know the false positive assessment is grounded because I ran the rule against normal system behavior before I called it stable.

Rules that have not passed all three gates are labeled "experimental." The label is there to keep the difference between a hypothesis and a finding honest.

The things the tool taught me that I did not expect

Wazuh has its own built-in detection rules that overlap with mine. When I first deployed the PowerShell encoded command rule, I searched for my custom rule ID in the dashboard and found nothing. The built-in rules had already caught the event first. In Wazuh, when a parent rule fires, child rules that chain off it can add context. But a parallel rule that covers the same event independently is never evaluated. The engine stops at the first match.

The fix is to chain your rule as a child of the relevant built-in rule rather than writing it as a parallel alternative. My rule now adds context on top of what Wazuh already detected, refining it rather than competing with it.

I would not have found this without testing against real events. A rule that never fires in a lab might be working perfectly, or it might be written in a way that guarantees it never evaluates. The only way to tell the difference is to make it fire.

Where this goes

The six rules currently in the repository cover five ATT&CK tactics: execution, credential access, persistence, defense evasion, and local account creation. I spread them across tactics on purpose, because a portfolio that covers only one phase of an intrusion shows a narrow view of how attacks actually unfold.

The next phase is OT and ICS techniques. Operational technology, the software that controls industrial equipment, runs on protocols designed before network security was a consideration. Modbus and DNP3 move control commands in plaintext. CISA publishes advisories about active exploitation of industrial systems. I am already pulling those advisories into the news aggregator on this site, so writing detection rules against them seems like the natural next step, and it narrows the portfolio toward a specific part of the field that does not get much attention. The repository is public if you want to check any of it for yourself.
