Zero Trust HTTP in Rust: What I Learned Building It

Published: 2026-09-12 · Code: github.com/mhebert-security/zero-trust-server

I built this server to find out what I did not know. At the start the reason was simpler and less dignified than that: I wanted to understand how HTTP actually works, not how a framework abstracts it. I set a constraint of standard library only, no unsafe, and one audited crate for TLS. It forced every decision into the open, because there was nowhere to hide a bad assumption behind a dependency.

This is the record of what those decisions cost me and what they taught.

Blocking I/O and thread-per-connection

I came into this knowing that async Rust was the idiomatic choice for a server. I chose blocking I/O anyway, and I underestimated how much friction that would create before I understood why it was right for this project.

Thread-per-connection is simple in a specific sense: the execution model maps directly to the mental model. One connection, one thread, one linear call stack. When something goes wrong, the stack trace tells you exactly where. In an async server the same failure produces a state machine unwind, and those require a different kind of reading.

The thing I kept coming back to is that simplicity is not the same as ease. A blocking server is simple to reason about and harder to operate at scale. An async server is easier to scale and harder to reason about under pressure. I was not choosing between better and worse. I was choosing what to optimize for, and I wanted understanding more than throughput. The blocking model let me hold the whole thing in my head.

The ceiling is real, though: too many connections exhaust the thread pool. I handle it with a semaphore. New connections past the limit receive a rejection and close immediately, so the server degrades gradually rather than collapsing. A hard ceiling I know about and control turns out to be safer than a soft ceiling I would only discover under load.

Parsing HTTP by hand

This is where I spent the most time and learned the most.

I thought parsing HTTP would be tedious. It was not. Every edge case represents a real decision someone had to make when the protocol was designed, and those decisions are not always obvious.

The one that cost me the most thought was chunked transfer encoding. HTTP/1.1 defines two ways for a client to declare how much body data it sends. Content-Length announces the total upfront. Transfer-Encoding: chunked sends data in size-prefixed segments without committing to a total. When a request carries both headers, RFC 7230 says Transfer-Encoding takes precedence. Not every proxy or load balancer implements that correctly. The gap between two different interpretations of the same request is exactly how HTTP request smuggling works.

I did not implement chunked encoding. A request that declares it is rejected at parse time. You cannot smuggle through an ambiguity that does not exist.

What I did not anticipate was how many subtle variations of malformed input I would need to handle. A lone carriage return in the request line, headers without values, methods not on my allowlist. Each one required a decision about what the correct response was, and each decision required reading the RFC rather than guessing. That habit, reading the spec before implementing, is the most durable thing this project gave me.

What I want to do next here is property-based testing with generated inputs, running the parser against hundreds of thousands of arbitrary byte sequences and checking that nothing produces undefined behavior or a panic. The parser is the highest-risk code in the project, and unit tests alone do not give it the verification it deserves.

TLS 1.3 only

I did not write my own TLS. That was the whole decision here.

The stdlib-only constraint was worth keeping everywhere I understood the problem well enough to solve it correctly. TLS is not one of those places. Getting it wrong does not produce incorrect output. It produces exploitable gaps in the encryption layer. rustls is written in safe Rust, reviewed by an independent security firm, and maintained by people who specialize in exactly this. Using it did not feel like a shortcut.

What this taught me is that knowing when to stop is a skill, and I did not have it to begin with. The instinct to own every layer is real and sometimes valuable, but it is also the thing that causes projects to ship homebrew TLS written by people who underestimated the problem. I underestimated it, which is why I did not write it.

I also changed my mind about why TLS 1.3 only was right. I first thought of it as a security decision, and it is. But it is also a design discipline: when you remove the compatibility surface, you remove the class of bugs that live in compatibility code. The server cannot negotiate a broken cipher suite because the negotiation path does not exist.

What comes next is post-quantum TLS. NIST finalized ML-KEM in 2024 and rustls supports the X25519MLKEM768 hybrid key exchange. Enabling it is a configuration change. I want to do it and document what it means to claim post-quantum resistance on a personal server, because most of the writing about PQC is abstract and I can make it concrete.

Proof of work

This was the most surprising part of the project to build.

I understood the concept before I started. A client proves it performed computation by finding a value that produces a hash with enough leading zero bits. The server validates with a single hash call, at constant cost regardless of how many clients are solving simultaneously.

What I did not understand until I built it is that the WASM integration is the hard part, not the algorithm. Getting the Rust solver compiled to WebAssembly, served as a static asset, and invoked correctly from JavaScript took more debugging than the SHA-256 implementation did. The algorithm is specified in a FIPS document and the vectors are published. WASM bindgen produces errors that are less clearly documented.

I also came to think differently about the threat model. The proof of work gate is not a security guarantee. It is a cost increase. A determined adversary with enough compute solves the puzzle and passes through. What the gate does is make automated scanning economically unappealing relative to the payoff, which is a more modest claim than "this stops attackers." I have tried to be precise about that distinction since.

The open question I keep thinking about is whether the difficulty can adapt automatically based on observed request patterns. A static difficulty is a static cost. An adaptive difficulty prices access by signal: high volume from one IP raises the floor, quiet periods lower it. It is roadmap task 13, and I find it genuinely interesting to design.

Session tokens

I chose stateful session tokens over signed cookies, and I spent more time on this decision than any other.

The argument for signed cookies is statelessness: the server holds nothing, any instance can validate any token, horizontal scaling is trivial. The argument against, which I eventually found more convincing, is that a compromised signing key validates every token ever issued. With stateful tokens, a compromised token is one session. You revoke it by removing it from the map.

What this taught me about system design is that the right answer depends on the threat model, not on what is idiomatic. Signed cookies are the right answer for a service operating across dozens of servers where the threat is session forgery. Stateful tokens are the right answer for a single-server deployment where the threat is key compromise and the cost of state is negligible. I spent a long time assuming one pattern was correct in the abstract, and it was not. The context decides, which took me longer to accept than it should have.

What I still want to improve is that the session model is binary. You either have a session or you do not. A capability token model would let the server issue sessions with specific permissions encoded in the token itself, verified without a lookup. That would be a more expressive form of zero trust: not just who you are, but what you are allowed to do and until when.

NixOS

This was the piece of the project I knew least about going in, and I learned the most from it in the least time.

The declarative model is not just a deployment convenience. It is a security property. A system whose entire state is declared in one version-controlled file cannot accumulate undocumented changes. There is no configuration drift because there is no mechanism for it. Every installed program, every running service, every network rule is either in the file or it does not exist on the machine.

The practical result was that I caught two configuration errors during the initial deployment that I would not have caught on a traditional system, because I was reading the entire configuration in one place. The errors were visible because everything was visible.

What I want to understand better is the tradeoff between declarative deployment and operational flexibility. NixOS makes routine changes slower and deliberate changes faster. That tradeoff is right for a server with a known, stable purpose. I am not sure it is right for every context, and I want a more precise account of when it is and when it is not.

What I did not solve

There is a nonce replay window. For 300 seconds after a valid proof of work solve, the nonce that authorized that session technically remains valid. A server that does not track consumed nonces will issue a new session for a replayed solve. I know this, and I am fixing it now. I am writing it down because the honest version of this project includes the things that shipped imperfect.

The admin login has no rate limit. The endpoint exists and the constant-time comparison exists, but the rate limit does not. A targeted brute force attempt against the admin password is currently possible. This is not a theoretical concern, and it is what I plan to fix next.

What comes next

The roadmap I have written for this project extends further than I expect to reach in the near term. Formal verification of the crypto core, hardware enclave session keys, a distributed attestation mesh, a zero-knowledge proof of work gate. These are not features I will ship next month. They are the version of the idea taken seriously over years.

The near-term list is more concrete: nonce replay prevention, post-quantum TLS, property-based crypto testing, MIRI verification, and writeup pages for the other three repos. Each one is a small unit of work that makes the project either more correct or more documented. Both matter.

What I want to hold onto, tentatively, is that every decision in this project traces back to a reason, and the reason is written down somewhere. Not a server where the security claims are asserted, but one where they can be checked, the constraints are visible, and the gaps are named by the person who knows them best.
