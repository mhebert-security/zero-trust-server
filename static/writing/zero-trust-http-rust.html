Zero Trust HTTP in Rust: What I Learned Building It

Published: 2026-09-12 · Code: github.com/mhebert-security/zero-trust-server

I started this project because I wanted to understand how HTTP actually works, meaning the protocol that carries most of the traffic on the web. Not how a framework hides it, but how a request arrives and what a server has to do with it. I set three constraints. Standard library only, no unsafe code, and one audited crate for TLS, which is the layer that encrypts the connection. Those constraints meant I could not hide a bad assumption behind a dependency. Every decision had to happen in the open, where I could see it.

I did not know how much I did not know when I started. This is what the project cost me and what it taught me, written as close to honestly as I can manage.

Blocking I/O and thread-per-connection

I knew before I started that async Rust was the usual choice for a server. I chose blocking I/O anyway, mostly because I could picture how it worked and I could not picture the other thing. I underestimated how much friction that choice would create before I worked out why it was right for this project.

Thread-per-connection is simple in one specific sense. The execution model maps directly to the mental model. One connection uses one thread, which runs one linear call stack. When something goes wrong, the stack trace points at the place. In an async server the same failure becomes a state machine unwind, and reading those is a different skill, one I do not have yet.

What I kept coming back to is that simplicity is not the same as ease. A blocking server is simple to reason about and harder to run at scale. An async server is easier to scale and harder to reason about under pressure. I was not choosing between a better approach and a worse one. I was choosing what to optimize for, and I wanted to understand the thing more than I wanted it to be fast. The blocking model let me hold the whole server in my head.

There is a ceiling either way. Too many connections exhaust the thread pool, so I bound it with a semaphore. New connections past the limit are rejected and close immediately. The server degrades gradually instead of collapsing. A hard ceiling I know about and control seems safer to me than a soft one I would only find under load, though I have not proven that with numbers.

Parsing HTTP by hand

I spent more time here than anywhere else, and I learned the most.

I expected parsing HTTP to be tedious. It was not. Every edge case is a decision someone made when the protocol was designed, and a lot of those decisions are not obvious until you have to implement them.

The one that cost me the most was chunked transfer encoding. HTTP/1.1 gives a client two ways to declare how much body data it is sending. Content-Length announces the total up front. Transfer-Encoding chunked sends the data in size-prefixed segments without committing to a total. When a request carries both headers, RFC 7230 says Transfer-Encoding wins. Not every proxy and load balancer implements that correctly. The gap between two readings of the same request is how HTTP request smuggling works.

I did not implement chunked encoding. A request that declares it is rejected at parse time. There is no ambiguity for a smuggled request to hide in, because the code path does not exist.

What I did not expect was how many small variations of malformed input I would need to handle. A lone carriage return in the request line, headers with no value, methods not on my allowlist. Each one needed a decision about the right response, and each decision meant reading the RFC instead of guessing. That habit, reading the spec before implementing, is the most useful thing the project gave me.

I would like to test the parser harder than unit tests can. Property-based testing would run it against hundreds of thousands of generated byte sequences and check that none of them produce undefined behavior or a panic. The parser is the riskiest code in the project, and I am not confident unit tests alone give it the coverage it needs.

TLS 1.3 only

I did not write my own TLS. That was the decision here.

The standard library constraint was worth keeping everywhere I understood the problem well enough to solve it correctly. TLS is not one of those places. Getting it wrong does not produce a wrong answer. It produces gaps in the encryption layer that someone can exploit. rustls is written in safe Rust, reviewed by an independent security firm, and maintained by people who work on exactly this. Using it did not feel like a shortcut.

What this taught me is that knowing when to stop is a skill, and I did not have it at the start. The instinct to own every layer is real and sometimes useful, but it is also how projects ship homebrew TLS written by people who underestimated the problem. I underestimated it, which is why I did not write it.

I also changed my mind about why TLS 1.3 only was right. I first thought of it as a security choice, and it is. But it is also a design discipline. When you remove the compatibility surface, you remove the class of bugs that live in compatibility code. The server cannot negotiate a broken cipher suite, because the path that would do the negotiating does not exist.

Post-quantum TLS is the thing I want to add next. NIST finalized ML-KEM in 2024 and rustls supports the X25519MLKEM768 hybrid key exchange. Enabling it is a configuration change. I would like to do it and then write down what it actually means to claim post-quantum resistance on a personal server. Most of what I have read about PQC is abstract, and I want to make it concrete.

Proof of work

This was the most surprising part to build.

I understood the idea before I started. A client proves it did some computation by finding a value that produces a hash, which is a fixed-length fingerprint of a piece of data, with enough leading zero bits. The server checks it with one hash call, at constant cost no matter how many clients are solving at once.

What I did not understand until I built it is that the WASM integration is the hard part, not the algorithm. WASM, or WebAssembly, is a format that lets compiled code run in the browser. Getting the Rust solver compiled to WASM, served as a static asset, and called correctly from JavaScript took more debugging than the SHA-256 implementation did. SHA-256 is specified in a FIPS document and the test vectors are published. WASM tooling produces errors that are harder to look up.

I also changed how I think about the threat model. The proof of work gate is not a security guarantee. It is a cost increase. A determined adversary with enough compute solves the puzzle and gets through. What the gate does is make automated scanning less worth the effort relative to the payoff, which is a smaller claim than stopping attackers outright. I have tried to be careful about that difference since.

I keep thinking about whether the difficulty could adjust on its own based on the requests I actually see. A fixed difficulty is a fixed cost. An adaptive difficulty would price access by signal, raising the floor when one address sends a lot of traffic and lowering it in quiet periods. It is roadmap task 13, and I find the design question genuinely interesting.

Session tokens

I chose stateful session tokens over signed cookies, and I spent longer on this than on any other decision.

The case for signed cookies is that the server holds nothing. Any instance can validate any token, and scaling out is trivial. The case against, which I eventually found more convincing, is that a compromised signing key validates every token ever issued. With stateful tokens, a compromised token is one session. You revoke it by removing it from the map.

What I took from this is that the right answer depends on the threat model, not on what is idiomatic. Signed cookies are the right answer for a service spread across dozens of servers where the threat is session forgery. Stateful tokens are the right answer for a single server where the threat is key compromise and keeping a little state is cheap. I spent a long time assuming one pattern was correct in the abstract, and it was not. The context decides, and that took me longer to accept than it should have.

The session model is still binary, and I would like to improve that. You either have a session or you do not. A capability token model would let the server issue sessions with specific permissions encoded in the token itself, checked without a lookup. That would be a more expressive form of zero trust, where zero trust means treating every request as unproven until it carries its own credentials, not just who you are but what you are allowed to do and until when.

NixOS

This was the part I knew least about going in, and I learned the most from it in the least time.

NixOS is a Linux distribution that builds its entire system from a single declarative configuration file. The declarative model is not just a deployment convenience. It is a security property. A system whose whole state is declared in one version-controlled file cannot accumulate undocumented changes. There is no configuration drift, because there is no way for drift to happen. Every installed program, every running service, every network rule is either in the file or it is not on the machine.

The practical result was that I caught two configuration errors during the first deployment that I would have missed on a traditional system, because I was reading the whole configuration in one place. The errors were visible because everything was visible.

I would like to understand the tradeoff better. NixOS makes routine changes slower and deliberate changes faster. That seems right for a server with a known, stable purpose, but I am not sure it is right for every context, and I do not have a clean account of when it is and when it is not.

What I did not solve

There is a nonce replay window. A nonce is the one-time value a client solves against in the proof of work. For 300 seconds after a valid solve, that nonce technically remains valid. A server that does not track which nonces it has consumed will issue a new session for a replayed solve. I know this, and I am fixing it now. I am writing it down because the honest version of the project has to include the things that shipped imperfect.

The admin login has no rate limit. The endpoint exists and the constant-time comparison exists, but the rate limit does not. A targeted brute force attempt against the admin password is possible right now. This is not a theoretical concern, and it is what I plan to fix next.

What comes next

The roadmap I have written extends further than I expect to reach soon. Formal verification of the crypto core, hardware enclave session keys, a distributed attestation mesh, a zero-knowledge proof of work gate. These are not features I will ship next month. They are the idea taken seriously over years, and I am not certain I will get to all of them.

The near-term list is more concrete. Nonce replay prevention, post-quantum TLS, property-based crypto testing, MIRI verification, and writeup pages for the other three repos. Each one is a small piece of work that makes the project either more correct or more documented. Both matter.

One thing I would like to hold onto, tentatively, is that every decision in this project traces back to a reason, and the reason is written down somewhere. I wanted a server where the security claims can be checked rather than asserted, the constraints are visible, and the gaps are named by the person who knows them best. I think that is what this is, or close to it.
