Executive Summary

An external threat actor conducted a targeted intrusion against Meridian's patient-facing web portal between 02:42 and 05:30 UTC on 2026-02-06. The attacker enumerated the application using four tools, identified a vulnerable endpoint, authenticated using credentials stolen directly from the server, and escalated to root. Before leaving, they exfiltrated the full patient database and established two separate backdoors designed to survive the active automated defence suite running on the host.

The defence suite detected and neutralised one backdoor but missed the second, which remained active at the close of the window. A network block on the attacker's C2 destination was logged but did not terminate the connection. Patient data left the environment. The incident is not contained.

INCIDENT NOT CONTAINEDPatient data left the environment, and the second backdoor at /opt/meridian/scripts/health_check was still running at the close of the window.

Blind spots

Sysmon killed before intrusion began. sysmon.service was removed by the first IR sweep at 03:08:19 UTC, before any attacker activity. Process-level telemetry (command lines, parent-child relationships) is absent for the entire attack window. No exec calls, no shell commands, no attacker tool invocations are visible in the logs.

Exact SQL injection payload unknown. No query-level logging survived in MeridianMySQL_CL that captures the specific SQLi string used during initial reconnaissance.

Exact database export query unknown. The mysqldump invocation is visible in the sysmon data captured before the defender sweep, but command arguments (table scope, filters) are not recoverable from surviving logs.

First backdoor staging method unknown. How /tmp/rootbash was written to disk is not evidenced in any surviving log source.

Exact credentials unknown. database.conf contents were not logged; the specific password used for the svc_backup SSH login is not recoverable.

C2 channel contents unknown. The SSH tunnel to 10.1.134.57:43212 is confirmed by network logs but its payload is encrypted and unrecoverable.

Network flow log absent. MeridianNetwork_CL contains only a point-in-time ss snapshot, not continuous flow records. Connection establishment times for the C2 tunnel are inferred, not directly evidenced.

Findings

F1 — Four-Tool Reconnaissance Chain

State it: The attacker used four distinct tools (nmap, curl, WhatWeb, gobuster) to map the web server over an 8-minute window starting at 03:47:32 UTC.

Show it: MeridianAccess_CL, ClientIp_s == "10.1.134.57". User-Agent strings: Mozilla/5.0 (compatible; Nmap Scripting Engine...) first seen 2026-02-06 03:47:32; curl/8.18.0 first seen 03:52:09; WhatWeb/0.6.3 first seen 03:54:54; gobuster/3.8.2 first seen 03:55:05.

Interpret it: The progression is deliberate — passive fingerprint (nmap), manual confirmation (curl), stack identification (WhatWeb), then wordlist coverage (gobuster). The attacker identified config_viewer.php manually via curl before gobuster ran, indicating prior knowledge or rapid manual analysis of the robots.txt or page structure.

F2 — LFI via config_viewer.php File Parameter

State it: The attacker successfully read /etc/passwd and database.conf from the server via an unsanitised file parameter in config_viewer.php at 04:07:59 and 04:08:34 UTC respectively.

Show it: MeridianAccess_CL. GET /config_viewer.php?file=../../../etc/passwd → HTTP 200 at 2026-02-06 04:07:59. GET /config_viewer.php?file=database.conf → HTTP 200 at 2026-02-06 04:08:34.

Interpret it: The file parameter accepts relative path traversal without sanitisation and is not scoped to an allowed directory. database.conf disclosure directly enabled the subsequent SSH login. The 35-second gap between the two reads suggests manual operation, not automated tooling.

F3 — Credential Reuse: svc_backup SSH Login

State it: The attacker authenticated via SSH as svc_backup using a password credential 57 seconds after reading database.conf.

Show it: MeridianAuth_CL. Accepted password for svc_backup from 10.1.134.57 port 39206 ssh2 at 2026-02-06 04:09:31. Preceding read: database.conf at 04:08:34.

Interpret it: High confidence the SSH password was sourced from database.conf. The 57-second gap is consistent with manual copy-paste and login. svc_backup is a pre-existing service account, not attacker-created.

F4 — Privilege Escalation via Pre-Staged SUID Binary

State it: The attacker achieved root via /tmp/rootbash -p, a SUID binary pre-staged in /tmp before or during the intrusion.

Show it: MeridianDefender_CL (SWEEP). Killing PID=265440 from /tmp (/tmp/rootbash -p) at 2026-02-06 05:05:01. Removed SUID: /tmp/rootbash at 05:05:06. No log source captures when or how the binary was placed in /tmp.

Interpret it: The binary was present when the attacker needed it, suggesting it was staged either via the web application (SQLi/webshell) or via the LFI/authenticated session before the SSH login. Staging method is a confirmed evidentiary gap. Medium confidence on staging vector.

F5 — Persistent Backdoor Surviving Defence Sweep

State it: A second root-level backdoor at /opt/meridian/scripts/health_check (PID 267155) was active and beaconing at window close, having survived the IR sweep.

Show it: MeridianSnapshot_CL (05:30:00 UTC). PID 267155, user root, started 04:51, parented to init (PID 1), exe symlink /proc/267155/exe -> /opt/meridian/scripts/health_check. MeridianDefender_CL SWEEP at 05:05:06: Non-baseline file in scripts/: health_check — no corresponding kill or removal action.

Interpret it: The binary was deliberately placed in /opt/meridian/scripts/ to blend with legitimate application infrastructure. The IR sweep's auto-remediation logic covers SUID binaries and /tmp processes only. A non-SUID binary in an application directory falls outside the cleanup rules. The process survived because the sweep's remediation scope was too narrow. The incident is not contained.

F6 — Patient Data Exfiltrated

State it: The full patient table was queried and patient data was exported to the attacker's IP before the SSH session was established.

Show it: MeridianDefender_CL. Full patient table query (DB) at 2026-02-06 02:58:26. Patient data export from 10.1.134.57 (WEB) at 03:56:28.

Interpret it: The 02:58:26 query predates the LFI and SSH login, indicating the attacker had web-application-level database access (likely via SQLi through the authenticated portal) independently of the credential theft chain. Patient data — medical records — left the environment. This is a confirmed data breach requiring regulatory notification assessment.

F7 — C2 Channel Active Through Established SSH Tunnel

State it: The health_check backdoor (and/or the existing SSH session) maintained an active C2 channel to 10.1.134.57:43212 that was logged as blocked but continued to transmit data throughout the window.

Show it: MeridianDefender_CL (NETWORK): 73 Blocked exfil to 10.1.134.57:43212 entries from 04:48:28 onward. MeridianSyslog_CL (kernel): concurrent NETMON_EXFIL entries showing outbound TCP packets with ACK PSH data to 10.1.134.57 DPT=43212 from SPT=22. The ACK PSH packets confirm data transmission, not just connection attempts.

Interpret it: The block rule logged but did not drop the connection. The existing SSH tunnel (established before the block rule triggered) was not terminated by the block. Blocking a destination after a session is established does not close that session. The C2 channel remained active.

F8 — Defence Stack Bootstrap Generated False Positive Detections

State it: The detection burst at 02:53:31 UTC represents the defence stack's own installation process, not attacker activity, and the IR sweep it triggered removed legitimate defensive tooling (sysmon).

Show it: MeridianDefender_CL: SSH key modifications, crontab modifications, and "New systemd service detected" at 02:53:31 — all auto-reverted within one second. First confirmed attacker activity: 03:47:32 UTC (54 minutes later). MeridianSyslog_CL: Stopped Sysmon event logger at 03:08:19 — removed by the same sweep cycle.

Interpret it: The IR sweep cannot distinguish attacker-planted services from legitimately installed defensive tooling. Removing sysmon eliminated the only source of process-level telemetry before the attack began. This is a design flaw in the sweep's baseline logic, not an attack technique.
