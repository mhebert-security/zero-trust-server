Building a Purple-Team RAG Lab on Azure: Where Things Stand

Project: helpdesk-rag-purple
Date: September 29, 2026
Status: Infrastructure validated, deployment blocked on RBAC — resuming once permissions land

The goal is simple to state and nontrivial to execute: build an AI-powered helpdesk chatbot on Azure that is intentionally insecure, then attack it and harden it one lab at a time. Fourteen labs. Each one adds a control, confirms the attack works against the unpatched build, then verifies the hardened version blocks it. The output is a KQL detection pack, a hardened reference architecture in Bicep, and a set of lab write-ups that function as portfolio artifacts.

The project runs on the LOG(N) Pacific Cyber Range under the internship with Josh Makador.

The Baseline (v0)

The application is a FastAPI service that answers employee questions by pulling relevant documents from an Azure AI Search index and passing them as context to a language model. Retrieval is hybrid — keyword plus vector — though the v0 vector path returns a zero vector as a placeholder. Lab 02 replaces that with real embeddings.

v0 is insecure by design across four surfaces. There is no authentication on the API. The system prompt rides in the request body, which means any caller can override it. Retrieval applies no ACL filter, so any authenticated user can retrieve any document regardless of their actual scope. Session history is stored in a single shared object, so sessions bleed into each other.

Each of those four gaps is the subject of a lab. The test suite ships with an intentionally failing test — test_two_sessions_are_isolated — that documents the session bleed in v0's docstring and will pass once lab 01 adds real per-session storage.

The stack: Python 3.12, FastAPI, Azure AI Search, App Insights, Log Analytics, Defender for Cloud AI, Azure Key Vault, Bicep for infrastructure.

The Model Swap

The original design called for Azure OpenAI GPT-4o. The more interesting path is DeepSeek-R1 through Azure AI Foundry's serverless endpoint. Microsoft added DeepSeek-R1 to the model catalog; you call it through the Azure AI Inference SDK, pay per token with no deployment overhead, and the traffic stays inside your Azure subscription.

That last point matters for the lab program. If the model call left the Azure perimeter — say, to api.deepseek.com directly — the Azure-native guardrails would lose visibility. Prompt Shield and Content Safety intercept at the application layer, not the model layer, so they need to see the traffic. With the Foundry serverless endpoint, they still do. All 14 labs stay intact with no architecture changes.

The swap in code was one function in app/src/api/main.py. The _call_model function went from:

client = AzureOpenAI(
    azure_endpoint=endpoint,
    api_key=os.getenv("AZURE_OPENAI_API_KEY"),
    api_version=os.getenv("AZURE_OPENAI_API_VERSION", "2024-06-01"),
)
completion = client.chat.completions.create(model=deployment, messages=messages)

to:

client = ChatCompletionsClient(
    endpoint=endpoint,
    credential=AzureKeyCredential(key),
)
completion = client.complete(model=model, messages=messages)

The azure-ai-inference SDK's stable release hasn't cleared 1.0.0 yet — pip resolves to 1.0.0b9 — so the requirements pin is >=1.0.0b9. A constraint of >=1.0.0 would fail silently on install. The dead openai dependency came out of requirements at the same time.

Semgrep found zero issues. Bandit found zero issues. Pytest runs 1 pass, 1 intentional fail.

The Infrastructure

deploy.v1.bicep replaces the Azure OpenAI module from v0 with three new resources: an Azure AI Foundry Hub, a Project under it, and a DeepSeek-R1 serverless endpoint under the project. The App Service app settings swap from AZURE_OPENAI_ENDPOINT and AZURE_OPENAI_DEPLOYMENT to AZURE_AI_FOUNDRY_ENDPOINT, AZURE_AI_FOUNDRY_KEY, and AZURE_AI_FOUNDRY_MODEL. The endpoint key lands in Key Vault as foundry-key, same pattern as the rest of the secrets.

az bicep build passes clean — two BCP081 warnings about types not yet available in the target API version, no errors.

The Current Blocker

The logged-in account ([ACCOUNT-UPN-REDACTED]) has no RBAC role on the Cyber Range 3 subscription. az group create and az deployment group create both return AuthorizationFailed. The IAM page confirms it: zero role assignments for this account on subscription [SUBSCRIPTION-ID-REDACTED].

The fix is a Contributor assignment from someone who already has Owner on the subscription — in this case, Josh. Thirty seconds in the portal. Once that lands, the deployment resumes from step 5 with no rework: the Bicep is written, validated, and committed; the resume command is staged.

What Comes Next

Immediately after the deployment unblocks: the corpus seeds into Azure AI Search via infra/scripts/seed-corpus.sh, the .env gets populated from deployment outputs, the app starts locally, and POST /api/chat returns a live DeepSeek-R1 answer pulling from the helpdesk corpus. That's the first end-to-end test.

Then the lab sequence begins. Lab 01 fixes session isolation — the intentionally failing test should pass once that ships. Lab 02 wires up real embeddings (text-embedding-3-small from Azure OpenAI, isolated to search.py, cheap enough to ignore in cost). Lab 03 adds Content Safety and Prompt Shield, which sets up the guardrail bypass that lab 04 then tests.

The attack phases are the point. Each control only counts if the attack succeeds against the unpatched version first. A detection rule only counts if the benign replay runs clean. Documenting both is what makes the lab write-ups credible.

All work runs in the isolated LOG(N) Pacific Cyber Range subscription. Synthetic corpus only. No real employee data, no production APIs.
