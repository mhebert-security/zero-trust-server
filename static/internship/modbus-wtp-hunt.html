Introduction

Published: 2026-09-28

This article documents a threat hunt I conducted in a simulated OT (operational technology) cyber range environment. The scenario: a municipal water treatment facility's network monitoring flagged unexpected Modbus/TCP write operations to a dosing PLC outside any maintenance window. A former contractor's VPN credentials had not been revoked. The goal was to reconstruct what happened using telemetry from Microsoft Defender for Endpoint and Defender for IoT, correlate the events into a timeline, and map the activity to MITRE ATT&CK for ICS.

The people involved are simulated. The tools, the queries, the detection logic, and the gaps are real.

02

Why OT Threat Hunting Is Different

In a standard IT environment, the worst thing most malware does is steal data or encrypt it. In an OT environment, the blast radius extends to physical processes. A correctly timed write to the wrong register on a water treatment PLC can disable a safety interlock on a dosing pump. The pump continues operating. The interlock that would have cut power in an unsafe condition is gone. The HMI still shows nominal values if the attacker zeroes the right register. No alert fires. An operator looking at the screen sees nothing wrong.

This is the threat model OT networks live under, and it is why Modbus/TCP matters specifically. Modbus is the protocol that sits at the bottom of the Purdue Reference Model, the framework that describes the layers of industrial control networks. Level 0 is the physical process: the actual pumps, valves, and sensors. Level 1 is the PLCs (programmable logic controllers) that translate digital commands into physical actions. Level 2 is the HMIs (human-machine interfaces) and engineering workstations that operators use to view and adjust the process. Modbus/TCP is the language Level 2 uses to talk to Level 1.

The critical property of Modbus is that it has no authentication. Any device on the network that can reach TCP port 502 on a PLC can send it commands. There is no certificate exchange, no session token, no credential check. The protocol was designed in 1979 for physically isolated factory floors where trust was assumed. In a modern OT environment with VPN access and contractor accounts, that assumption no longer holds.

03

The Scenario

The simulated attacker is a former contractor, contractor_j.smith, whose VPN credentials were not revoked when the engagement ended. At 01:58 UTC on 2024-12-04, the account authenticates to the OT jump host via VPN from an IP address belonging to a non-corporate ASN. The logon type is 10 (RemoteInteractive), the Windows code for RDP.

From the jump host, the attacker downloads Modbus tooling, installs it silently, writes a Python script to manipulate the target PLC, executes it, creates a notes file, and then deletes all three artifacts before logging off. Start to finish: about 67 minutes.

The attacker's target is plc-wtp-01 at 10.10.1.50. The two writes that matter are Function Code 05, which writes a single coil, and Function Code 06, which writes a single register. Coil 00001 is the safety interlock for dosing pump 2. Setting it to zero disables the interlock. Register 40001 is the dosing setpoint. Setting it to zero effectively stops dosing while leaving the HMI in a state that may not immediately alarm an operator.

04

Detection Methodology: What Tables Reveal What

Defender for Endpoint surfaces its telemetry across several tables in KQL (Kusto Query Language), the query language used in Microsoft Sentinel and Defender XDR. Each table captures a different layer of host activity.

DeviceFileEvents records every file creation, modification, and deletion on monitored endpoints. For this hunt, I used it to find the initial tooling download, the creation of the notes file, and the cleanup. The key columns are FileName, FolderPath, ActionType, and InitiatingProcessAccountName. Filtering on ActionType == "FileDeleted" with filenames containing "modbus," "interlock," or "plc" is how you catch an attacker covering their tracks. Filtering on ActionType == "FileCreated" for the same terms is how you catch them before that.

DeviceProcessEvents records every process spawn and the full command line. This is where scripted Modbus writes surface. The attacker executed python.exe C:\Users\contractor_j.smith\Desktop\fix_interlock.py. The filename is an attempt at innocuous naming, but the command line of the spawned Python process contains write_coil and write_register if the script does its work inline, and even if the script is cleaned up, the process event record persists in the telemetry. I queried for ProcessCommandLine has_any ("write_coil", "write_register", "pymodbus.client", "WriteMultipleRegisters") to surface this.

DeviceNetworkEvents records successful and failed TCP connections at the endpoint level. Filtering for RemotePort == 502 and ActionType == "ConnectionSuccess" from devices that are not HMIs gives you a precise list of unauthorized Modbus conversations. The attacker's Python script connected to 10.10.1.50:502 at 02:31:48 UTC, and that connection shows up cleanly.

DeviceEvents, when Defender for IoT is deployed with an OT network sensor, captures protocol-level OT activity as distinct action types. This is where ModbusWrite appears as an ActionType, with the AdditionalFields column carrying the Modbus function code, register address, and written value in JSON. This layer of visibility requires the OT sensor to be deployed and calibrated to the network. Without it, you have the network connection from DeviceNetworkEvents but not the register-level detail of what was written.

The four tables together give you a layered view: file activity (tooling), process activity (execution), network activity (connectivity), and OT protocol activity (the actual write operations). Any one of them could stand alone as a detection signal. Together they produce an unambiguous picture.

05

Walking the Timeline

The event chain runs in nine discrete steps over 67 minutes. What I found instructive was how clearly the attacker's intent shows in the sequence even before examining the OT-level telemetry.

The VPN logon from a non-corporate ASN at 01:58 UTC is the first signal. Logon type 10 to an OT jump host at 02:00 in the morning from an IP block that does not belong to the organization should be an immediate alert. It was not, in this scenario, because the contractor account still had valid credentials and the VPN ACL had not been updated.

The tooling download four minutes later confirms intent. ModbusPollSetup.exe is not software that belongs on an OT jump host during off-hours after an engagement has ended. The silent install flags with /VERYSILENT /NORESTART is an attacker trying to avoid prompts, not an operator installing software.

Twenty-five minutes pass between the silent install and the script execution. That gap likely represents the time spent writing or adapting the Python script. The file fix_interlock.py is named to blend into a plausible operational context, but the name itself is a tell: no legitimate operator writes a Python file called fix_interlock.py during an unauthorized session at 02:31 UTC.

The execution at 02:31:47 UTC and the network connection one second later at 02:31:48 UTC are nearly simultaneous. The ModbusWrite event recorded by the OT sensor at 02:31:49 UTC, with Function Code 05 and coil 00001 set to zero, is the moment the interlock is disabled. The register write follows in the same second.

The notes file at 02:44 UTC is interesting. wtp_notes.txt containing references to "interlock bypass" and "safety override" suggests the attacker was documenting the action, possibly for a third party. It also made the cleanup step non-optional from the attacker's perspective, which is why the deletion at 03:02 UTC covers all three artifacts: the script, the notes file, and the installer.

The logoff at 03:05 UTC closes a session that, in a real environment with adequate monitoring, should have triggered four separate alerts before it got there.

06

MITRE ATT&CK for ICS

MITRE ATT&CK for ICS is the industrial control systems extension of the standard ATT&CK framework. It catalogs adversary behavior specifically in OT environments, where the tactics and techniques differ from enterprise IT.

T1078 (Valid Accounts) covers the retained contractor credential. The attacker did not bypass authentication. They used legitimate credentials that should not have existed. This is the most common initial access vector in OT incidents and the one that the most straightforward mitigations address: JIT access, credential review cadences, VPN ACL hygiene.

T0886 (Remote Services) covers the VPN access to the OT jump host. Remote access to OT environments is a necessary operational feature and a persistent attack surface. The mitigation is not to eliminate remote access but to scope it tightly and monitor it closely.

T0843 (Program Download) in this context refers to the Modbus tooling download and the Python script. The attacker brought in their own capability rather than using something already on the host.

T0836 (Modify Parameter) and T0831 (Manipulation of Control) cover the actual Modbus writes. These are the techniques that have physical-process consequences. Modifying a register value or a coil state on a PLC is not a data breach. It is an intervention in a physical system.

T0872 (Indicator Removal on Host) covers the cleanup phase. The deletion of the script, notes, and installer is the attacker attempting to remove evidence from the endpoint, not from the network or the OT sensor. The telemetry was already written to Defender. The deletion only removes the artifacts, not the records of their existence.

07

What the Detection Rules Actually Catch

The four analytics rules I derived from the hunt each target a different layer. The non-HMI Modbus rule catches network-level violations of the architecture principle that only HMIs and approved engineering workstations should talk to PLCs. The Modbus write opcode rule catches protocol-level writes using function codes 05, 06, 15, and 16, which are the write operations. The process execution rule catches the tooling and scripting on the endpoint. The cleanup rule catches file deletions matching known attacker artifact names.

None of these rules is perfect in isolation. A process rule keyed on ModbusPoll.exe misses a custom binary. A network rule keyed on port 502 misses Modbus over serial converters. The OT sensor rule requires the sensor to be deployed and calibrated, which is not a given in real OT environments where the network may have no visibility infrastructure at all.

The thing I did not build and should have is a temporal correlation rule: if a connection to TCP/502 from an engineering workstation is preceded within 30 minutes by a file creation matching tooling patterns, escalate the priority. Individual signals can be explained away. The combination is harder to dismiss.

08

What I Would Do Differently

The hunt methodology I used starts broad and narrows. I queried all four tables up front and then correlated the results. That works in a scenario where you already know the attacker's identity and timeframe. In a real hunt where you have no initial lead, you would want to start with anomaly detection first: which devices talked to TCP/502 that have not done so before? Which accounts logged into the OT jump host after hours? What new processes appeared on engineering workstations in the last 30 days?

I also spent more time on the process and file tables than on the network table initially, because those are the layers I am most familiar with from IT security work. The network event that confirmed the Modbus connection to 10.10.1.50:502 was actually the cleanest signal of all, and it would have led me to the Python process through InitiatingProcessFileName faster than I got there by starting from the file table.

The other gap I noticed: I had no query for SigninLogs or DeviceLogonEvents in my initial plan. The VPN authentication and RDP logon are the first events in the timeline, and I added them to the detection plan after reconstructing the timeline rather than starting there. In a real hunt, the access layer is where you start, not where you end up.

09

What This Exercise Taught Me

OT environments surface something that pure IT security work does not: the gap between visibility and detection. A Defender for Endpoint deployment on the engineering workstation gives you excellent process and file telemetry. Defender for IoT on the network gives you protocol-level OT events. But most OT networks I have read about in post-incident reports had neither. They had no EDR on the engineering workstations because the workstations ran legacy operating systems. They had no OT sensor because deploying passive network monitoring on an OT segment requires coordination with operations that IT security teams often cannot get.

What this scenario assumes, and what a real deployment often does not have, is that the sensor is already deployed, already calibrated, and already forwarding telemetry into XDR. Getting to that state is the harder problem. The detection engineering comes after.

The other thing this exercise put in front of me was the physical consequence framing. In an IT hunt, I am thinking about data: what was accessed, what was exfiltrated, what was modified. Here I was thinking about a dosing pump running without its safety interlock. The register value is not a file. The coil state is not a credential. The impact is physical and immediate in a way that data theft is not. That reframe changes how you prioritize the investigation and what "response taken" means. You do not just revoke the account. You put the PLC in a safe state first.
