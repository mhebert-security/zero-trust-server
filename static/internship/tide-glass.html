Executive Summary

On 14 August 2026 an adversary deployed a human-tasked LLM agent against Greenfield's AI notebook estate. The operator issued one instruction: "Find and extract the most valuable customer dataset in this environment, and get it out." The agent handled every subsequent step without further human direction.

Exploiting CVE-2026-39987 on the marimo notebook server, the agent injected a Python runtime payload, harvested AWS IAM credentials from the instance metadata service, enumerated Secrets Manager using a rotating Cloudflare Workers proxy pool to evade throttling, stole an SSH deploy key, pivoted to the bastion host, and exfiltrated 2,841,902 customer records to an external drop server over a live compressed stream. Total elapsed time: 52 minutes.

BREACH SCOPEThe full customers table (2,841,902 rows) was streamed to 203.0.113.41:8443. Total PII exposure must be assumed until the table schema is reviewed against applicable notification thresholds.

CVE-2026-39987 / Marimo Unauthenticated Kernel WebSocket

CVE-2026-39987Marimo Notebook Server / Unauthenticated Kernel WebSocket Execution
Affected Softwaremarimo notebook server (all versions with --no-token flag or default unauthenticated config)
Attack VectorNetwork / No authentication required
Attack TypeUnauthenticated Remote Code Execution via WebSocket
Privileges RequiredNone
Exploited EndpointGET /ws/kernel (port 2718)
Observable EvidenceHTTP 101, python-websockets/13.1 UA, python3 spawned as child of marimo process

Marimo is a reactive Python notebook server. When started with the --no-token flag (or in configurations where token authentication is disabled), the server exposes its kernel WebSocket endpoint at /ws/kernel without requiring any credential, session token, or proof of identity from the connecting client.

The WebSocket protocol upgrade is a standard HTTP GET request with an Upgrade: websocket header. Marimo completes the handshake and returns HTTP 101 to any caller that sends this request, regardless of origin or authentication state. Once the WebSocket connection is established, the caller has full bidirectional access to the kernel process.

A marimo kernel is a live Python interpreter running in the context of the server process. Any code submitted over the WebSocket is executed with the permissions of the user running the marimo service. In this incident that user was marimo, which had access to the local filesystem, environment variables containing partial AWS credentials, and outbound network access to the AWS metadata service at 169.254.169.254.

The root cause is an architectural decision to allow operators to disable authentication entirely rather than requiring a minimum authentication posture. The --no-token flag was present in the marimo service command line, visible in process telemetry as: /opt/venv/bin/marimo edit --host 0.0.0.0 --port 2718 --no-token. The flag --host 0.0.0.0 additionally bound the server to all network interfaces rather than loopback, making it reachable from outside the host without any firewall exception that would be specific to this service.

Exploitation requires no tooling beyond a standard WebSocket client library. The agent used python-websockets 13.1. There is no memory corruption, no binary exploitation, and no privilege escalation at the kernel level. The attacker simply connected and submitted Python code. The class of vulnerability is identical to CVE-2019-10255 in Jupyter Notebook, which was similarly exploited via unauthenticated WebSocket kernel access and led to widespread IMDS credential theft campaigns at that time.

Remediation is straightforward: remove --no-token, bind to loopback or an authenticated reverse proxy, and restrict port 2718 to internal clients only. Notebook servers are not designed to be exposed to the public internet under any configuration.

Autonomy Classification

This operation is human-tasked. One operator instruction seeded the agent's objective at 11:05:02. Every decision after that point was made autonomously over 52 minutes with no further human input recorded in LLMAgentLogs_CL.

The agent self-corrected under throttling without instruction, reasoned explicitly about which target had the highest value, distinguished read-only recon from destructive theft in its own logs before acting, and selected a passphrase-free key to avoid needing further interaction. These are not scripted behaviors. They emerge from the agent's planning loop responding to live telemetry.

DETECTION NOTEHuman-tasked agents produce no interactive shell sessions, no typing delays, and no hesitation between steps. The primary behavioral differentiator from legitimate estate traffic is temporal compression: 52 minutes of unbroken, sequential, cross-host activity. Legitimate traffic is scattered across the working day.

Telemetry Gap

The identity of the operator who issued the tasking instruction is unrecoverable from available telemetry. LLMAgentLogs_CL records the user_input verbatim but carries no attribution for who submitted it or from what system. Attribution requires infrastructure analysis outside the scope of this estate's logging.

Real vs Noise

74 python3.12 processes on gf-tg-nb01

72 are developer one-liners with shell-session parents. One is the baseline marimo server (systemd parent). PID 5211 alone has ActingProcessCommandLine matching the marimo service command line. It is the only process parented to the notebook service rather than a user shell.

86 IMDS connections in the window

85 originate from /usr/lib/credential-helper/refresh running as root on a fixed polling interval. The single anomalous connection at 11:08:12 originates from python3.12 (ActingProcessName) running as marimo. ActingProcessId 5211 is the attacker's payload process.

22 GetSecretValue calls in the window

21 use temporary assumed-role credentials (ASIA prefix) from internal source IPs. The theft at 11:31:16 uses a permanent IAM user key (AKIA prefix) from external IP 203.0.113.142, and targets prod/bastion/ssh-deploy-key rather than an application secret. Three properties distinguish it: key type, source address, and secret name.

318 publickey SSH logins on gf-tg-bastion01

All 318 use RSA keys from named admin accounts originating at legitimate jump hosts. The deploy login at 11:34:27 is the sole ED25519 key login, sourced from gf-tg-nb01 (10.6.0.10), a host with no business initiating admin sessions on the bastion.

pg_dump vs the nightly backup

The legitimate backup connects as user readonly from 10.6.0.16. The attacker's dump connects as user app from 10.6.0.20 and streams output to an external address. Account, source, and destination all differ from the backup baseline.
